# Phase 5 Task 5.2 — Contest Draft Review & Approval Workflow (LOCAL ONLY)

## Executive Summary

Phase 5 Task 5.2 implements a secure, deterministic, local-only human review workflow for `ContestDraft` objects generated by Phase 5 Task 5.1. The workflow enables human reviewers (such as merchant risk managers or dispute specialists) to inspect a local contest draft and record an explicit `APPROVE` or `REJECT` decision.

### Critical Safety Boundary
- **LOCAL ONLY Workflow**: ZERO Razorpay mutation API calls (`POST` contest, `PATCH` dispute, `PUT` dispute, `DELETE` dispute, dispute acceptance, dispute rejection, evidence submission, payment modification).
- **Core Invariant**: `"Generate locally → Review locally → Never mutate Razorpay."`
- **Zero AI / External Calls**: Zero LLM invocations, zero embedding calls, zero external network traffic during review.
- **Financial Immutability**: Financial fields (`payment_id`, `amount`, `currency`) on the underlying `Dispute` are strictly immutable and verified before and after every review operation.

## 1. Architectural Design & State Separation

### 1.1 Strict Status Separation
The system maintains two independent status fields on `ContestDraft`:

1. `ContestDraft.status`: Policy-derived state (`DRAFT`, `REVIEW_REQUIRED`, `BLOCKED`).
   - Determined authoritatively by Phase 5 Task 5.1 based on `PolicyResult`.
   - **Immutable to human review operations**. Human review NEVER changes `ContestDraft.status`.

2. `ContestDraft.review_status`: Human review state (`PENDING_REVIEW`, `APPROVED`, `REJECTED`).
   - Modified **exclusively** by Phase 5 Task 5.2 human review operations.
   - Initial state when generated is `PENDING_REVIEW`.

```
Policy State (status)           Human Review State (review_status)
---------------------           ----------------------------------
DRAFT                ─┐         PENDING_REVIEW (Initial)
REVIEW_REQUIRED      ─┼───────►        │
BLOCKED              ─┘         ┌──────┴──────┐
                                ▼             ▼
                             APPROVED      REJECTED
```

### 1.2 Review State Machine Rules

| Initial `status` | Initial `review_status` | Action | New `review_status` | `status` | HTTP Code |
|---|---|---|---|---|---|
| `DRAFT` | `PENDING_REVIEW` | `APPROVE` | `APPROVED` | `DRAFT` | 200 OK |
| `DRAFT` | `PENDING_REVIEW` | `REJECT` | `REJECTED` | `DRAFT` | 200 OK |
| `REVIEW_REQUIRED` | `PENDING_REVIEW` | `APPROVE` | `APPROVED` | `REVIEW_REQUIRED` | 200 OK |
| `REVIEW_REQUIRED` | `PENDING_REVIEW` | `REJECT` | `REJECTED` | `REVIEW_REQUIRED` | 200 OK |
| `BLOCKED` | `PENDING_REVIEW` | `APPROVE` | *Rejected* | `BLOCKED` | **400 Bad Request** |
| `BLOCKED` | `PENDING_REVIEW` | `REJECT` | `REJECTED` | `BLOCKED` | 200 OK |
| Any | `APPROVED` | `APPROVE` | `APPROVED` | Unchanged | 200 OK (Idempotent) |
| Any | `REJECTED` | `REJECT` | `REJECTED` | Unchanged | 200 OK (Idempotent) |
| Any | `APPROVED` | `REJECT` | *Rejected* | Unchanged | **409 Conflict** |
| Any | `REJECTED` | `APPROVE` | *Rejected* | Unchanged | **409 Conflict** |

## 2. Stale Draft Protection & Canonical Fingerprinting

To prevent human reviewers from approving out-of-date drafts when upstream evidence or policy results have changed:

1. **Shared Canonical Helper**: `backend/app/services/contest_draft_fingerprint.py`
   - Recomputes SHA-256 hash over normalized inputs: `dispute_id`, `payment_id`, `amount`, `currency`, `policy_result_id`, `policy_version`, `policy_outcome`, `match_results` (sorted by fact name and document ID), `documents` (sorted by ID), `generator_version`, and `draft_version`.
   - Normalizes Enum types (`getattr(val, "value", str(val))`) to guarantee bit-identical hashes across in-memory models and reloaded DB entities.
2. **Validation on Review**: If the recomputed input fingerprint differs from `ContestDraft.input_fingerprint`, a `StaleDraftException` (HTTP 409 Conflict) is raised, preventing approval/rejection of stale content.

## 3. Concurrency Safety & Audit Logging

### 3.1 Concurrency Safety (Atomic UPDATE)
To prevent race conditions where two reviewers attempt to review the same draft simultaneously:
```sql
UPDATE contest_drafts
SET review_status = :new_review_status,
    reviewed_at = :now,
    reviewer_reference = :reviewer_reference,
    review_comment = :comment
WHERE id = :draft_id AND review_status = 'PENDING_REVIEW';
```
- If `affected_rows == 1`: Update succeeded. A single audit record is committed.
- If `affected_rows == 0`: Another reviewer won the race. The transaction rolls back and an idempotent check handles identical/conflicting decisions.

### 3.2 Append-Only Review Audit Log (`ContestDraftReviewAudit`)
Every review decision creates exactly one immutable audit entry in `contest_draft_review_audits`:
- `id` (UUIDv4)
- `draft_id` (FK to `contest_drafts.id`)
- `dispute_id` (String)
- `decision` (`APPROVE` or `REJECT`)
- `previous_review_status`
- `new_review_status`
- `reviewer_reference` (Identification metadata only)
- `comment` (Sanitized plain text, max 2000 chars, zero instruction injection risk)
- `created_at` (UTC timestamp)
